Lectura: al superar memory.max (402653184 = 384Mi) el OOM killer del kernel actuó dentro del cgroup del contenedor
(oom_kill 1), pero con memory.oom.group=0 mata solo al proceso más grande: el sh del experimento que retenía los 500 MB
(por eso kubectl exec terminó con 137). El proceso principal (dotnet, PID 1) siguió vivo, el contenedor no se reinició
(Restart Count sigue en 1) y el pod nunca dejó de estar Ready: el usuario no ve el fallo.
El plan esperaba "OOMKilled y reinicio del contenedor"; eso pasa solo si el que crece es el proceso principal o si el
runtime activa memory.oom.group (cri-dockerd, el runtime de este cluster, no lo activa). La muerte y el reinicio del
proceso principal están medidos aparte con measure-mttr.sh --crash (docs/evidencia/C09/03-cluster-mttr.txt).
